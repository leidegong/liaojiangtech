# 图数遥融合链路 MVP

一个可运行的单机实验：JPEG 视频、10 Hz 模拟遥测、50 Hz 遥控状态，通过**同一个受限双向 UDP 链路**传输。用 FIFO 与 Fusion 两种调度器对比拥塞下的控制延迟；视频默认**分层**发送（160×90 基础层每帧必发 + 按剩余容量选档的高清层），拥塞时画面降质但不停顿；高清层带按实测丢包率配置的 Reed-Solomon **FEC**，随机丢包时仍能整帧还原。测到长突发时，调度器把相邻 2～3 帧的高清分片**交错发送**，并把冗余按突发长度略增，使一串连丢摊到多个码字上而不是打穿同一帧。它验证算法机制，不复现 NEBULA-7 的射频、硬件或实机性能。

已完成的测试和实测结果见 [VERIFICATION.md](VERIFICATION.md)。

## 操作与实验

1. 选择 **FIFO**，把容量设为 **5 Mbps**，等待指标稳定。
2. 把容量降到 **500 kbps**，保持 10 秒以上，观察 FIFO 队列和遥控 P99。
3. 切换 **Fusion**，保持相同容量，等待 5 秒滚动窗口更新。
4. 对比控制延迟、视频 FPS、画面年龄和丢帧数。默认的分层视频此时只剩基础层：画面变糊，但仍约 15 FPS、约 60 ms 画面年龄。
5. 在“视频编码”中切到 **单层**，对比原来的整帧丢弃行为：同样容量下只有约 2 FPS、约 550 ms。
6. 切回分层，把容量逐级调到 1.5、5 Mbps，观察画面角标和设置面板中高清层档位的变化。
7. 保持 5 Mbps，把随机包丢失调到 5%：“高清层 FEC”下显示实测丢包率、每帧冗余包数和已救回的帧数，画面仍几乎全是高清。再切到 **关闭**：画面仍然流畅（每帧高清丢了就由基础层顶上），但高清占比降到约三分之一。
8. 保持 5% 丢包，把“丢包突发长度”调到 4 以上：平均丢包率不变，丢失变成成串连续发生。FEC 说明里会出现“2 帧交织”或“3 帧交织”；高清层仍应大部分可还原（一串连丢被摊到相邻几帧上）。再切到 **关闭** FEC：交织不再启动，高清帧会大量丢失，由基础层顶上。
9. 单独调整传播时延、抖动、随机包丢失，观察完整帧的接收情况。

键盘操作（先点击视频画面）：

| 按键 | 作用 |
|---|---|
| W / S | 油门增加 / 减少，松开后保持 |
| A / D | 偏航，松开归零 |
| ↑ / ↓ | 俯仰，松开归零 |
| ← / → | 横滚，松开归零 |
| Space | 油门回到 50%，其余轴归零 |

也可以按住网页按钮。界面显示“地面输入 / 机载执行”，后者由遥测回传。模型的高度、航向、位置会随已收到的控制变化。窗口失焦会归中；1 秒收不到网页心跳则地面输入归中；机载侧不执行生成时间超过 500 ms 的控制状态。以上只是模拟模型行为，不是飞控失效保护实现。

网页以 10 Hz 更新操作状态；**Ground Node 独立以 50 Hz 生成无线控制包**。没有打开网页时仍持续发送中立控制，方便无界面实验。

## 一键生成可复查的 A/B 结果

```bash
.venv/bin/python -m nebula_mvp.benchmark --verify
```

Windows：`.\.venv\Scripts\python.exe -m nebula_mvp.benchmark --verify`。

三组依次运行，使用同一个合成源与种子：`naive`（FIFO + 单层）、`fusion`（Fusion + 单层）、`fusion-layered`（Fusion + 分层）。前两组复现原来的 FIFO/Fusion 对比，第三组只改变视频分层。每组 5 Mbps 预热 3 秒，然后降到 500 kbps 运行 10 秒，统计最后 5 秒。程序检查控制样本数、Fusion 控制 P99、FIFO/Fusion 的延迟差异、完整视频帧、总带宽上限；分层组另查遥控 P99、显示帧率（≥10 FPS 且 ≥ 单层 3 倍）、视频 P95 延迟、最长冻结、容量骤降后 3 秒内的最长冻结，以及 5 Mbps 下确实在用高清层。每组还检查模拟器本身的保真度（见“计时”）：空口时间没有因主机卡顿而丢失（节拍效率 ≥ 0.98），投递时刻比模型晚得不多（P95 < 5 ms）；主机过忙时判定本次无效。

```bash
# 丢包场景：容量保持 5 Mbps，预热后开始 5% 随机丢包
.venv/bin/python -m nebula_mvp.benchmark --scenario loss --verify
```

三组依次加上分层和 FEC：`fusion`（单层）、`layered`（分层，无 FEC）、`layered-fec`（分层 + FEC）。除了上面的保真度和带宽检查，还查三组遥控 P99、无 FEC 时高清帧确实大量无法还原（≥30%）但画面不停顿（显示帧率 ≥13 FPS、最长冻结 <300 ms；两层同时丢失的采集约占 6%，上限约 14.1 FPS，相邻两次采集都两层全丢时画面会停约 200 ms），以及 FEC 组稳态下无法还原的高清帧 ≤2%、高清占比 ≥90%、显示帧率 ≥14 FPS、视频 P95 延迟 <250 ms。“稳态”指切换 3 秒之后；前 3 秒丢包率估计还在追赶，单独列出，不做判定。

```bash
# 突发丢包场景：平均丢包仍为 5%，但成串连续丢失，平均突发长度依次为 1、2、4、8、16 个包
.venv/bin/python -m nebula_mvp.benchmark --scenario burst --verify
```

五组都是分层 + FEC，只改变突发长度，每组切换后运行 20 秒（长突发次数少，统计需要更长时间）。表中列出信道实际测到的丢包率和平均突发长度，用于核对模型；无法还原的高清帧、显示的采集帧比例、高清占比、帧率和最长冻结都统计切换 3 秒之后的整段时间。验收检查实测丢包率和突发长度落在按“几何分布连丢次数之和”估算的 3 倍标准差之内、各组遥控 P99 <250 ms、突发长度 1 时无法还原的高清帧 ≤2%、更长突发在交织后无法还原的高清帧分别有上限（2 / 4 / 8 / 16 为 5% / 6% / 8% / 12%），以及模拟器保真度。

抖动和丢包由 `--seed`（默认 7）驱动。同一个种子重跑时，信道的丢包序列几乎相同（只按预热期发包数错开几个包），重复的是系统计时的波动而不是信道统计；要独立样本就换种子。

三个场景的 `--mbps`、`--loss`、`--burst` 都指切换后的状态；预热阶段始终是 5 Mbps、无丢包，这样预热快照才是干净的基线。`--seconds` 的默认值按场景不同（拥塞、丢包 10 秒，突发 20 秒）。

## 实现结构

```text
Air Node                                        Ground Node
  OpenCV ─┬→ 160×90 JPEG ─ VIDEO_BASE ─┐   ┌──→ 分层重组(FEC 还原) → 选层 → 解码校验 → 网页视频
          └→ 阶梯选档 JPEG + FEC ─ VIDEO┤   │
             ↑ 高清层预算 / 丢包率      │   │
  模拟飞控 10 Hz ────────── DATA ──────┤   ├──→ 遥测与机载控制值
                                      ▼   │
                              Link Emulator
                           同一个共享发送调度器
                           同一条虚拟发送时间线
                            同一个串行发送资源
                            延迟 / 抖动 / 丢包
                                      ▲   │
  执行模拟控制 ←─────────── CONTROL ───┘   └──── 键盘状态 → 50 Hz
```

三个节点是一个 Python 进程中的独立 asyncio UDP endpoint，各自绑定随机本机端口。它们确实通过 socket 收发，便于单命令启动和同一时钟计时；本版没有拆成三个独立进程。

HTTP 仅用于地面画面展示、观测指标、键盘输入和模拟器设置。Ground Node 收到键盘状态后仍必须发出 CONTROL UDP 包，经链路调度、限速和时延后才到达 Air Node。网页视频只读取 Ground Node 已重组并解码校验的 JPEG。观测接口不额外消耗模拟无线带宽。

| 模块 | 职责 |
|---|---|
| `protocol.py` | 二进制封包、JPEG 分片、有界重组（任意 k 片还原）、含冗余的视频字节预算换算 |

| `link_emulator.py` | 唯一瓶颈、双向调度、传播时延、抖动、随机丢包、高清层预算、丢包率估计 |
| `metrics.py` | 包时间戳、P50/P95/P99、按帧（跨层）统计、最长冻结、模拟器保真度、CSV |
| `air_node.py` / `ground_node.py` | 两端真实 UDP 接口、分流与业务交付、地面选层显示 |
| `video.py` / `telemetry.py` / `control.py` | 视频源与高清层码率阶梯、模拟运动模型、控制量验证 |

## 协议

网络字节序，固定头 18 字节：

| 字段 | 字节数 | 定义 |
|---|---:|---|
| magic | 2 | `N7` |
| version | 1 | `2`（加入 FEC 时分片头变更；版本 1 的包会被拒收） |
| type | 1 | VIDEO=1（全分辨率层），DATA=2，CONTROL=3，VIDEO_BASE=4（基础层） |
| sequence | 4 | 无符号序号 |
| timestamp | 8 | `perf_counter_ns()` 生成时间 |
| payload_length | 2 | 载荷长度 |

VIDEO 与 VIDEO_BASE 的载荷前 12 字节是 `frame_id:uint32, fragment_id:uint16, fragment_count:uint16, frame_bytes:uint32`。`fragment_count` 包含 FEC 冗余片；数据片数由 `frame_bytes` 算出（向上取整除以 1170），编号在它之后的是冗余片，长度等于第一个数据片。任何一片都描述了整帧的布局，所以接收端从任意片就能开始组帧。同一次采集的两层共用 frame_id 和时间戳。每个 UDP 应用数据报最多 1200 字节，因此每片 JPEG 最多 1170 字节；解析时逐片校验长度与布局一致。DATA/CONTROL 的载荷是 JSON。时钟不适用于跨电脑直接测单程延迟；将来拆成多台电脑，需要时钟同步或采用往返测量。

## 调度与模型边界

- **Fusion CONTROL：** 一个最新值槽，优先级最高，100 ms TTL。等待令牌时会重新选择优先级，不让选中的视频包长期占住调度器。
- **Fusion DATA：** 最多 100 包，超过上限丢最老数据；500 ms TTL。
- **Fusion VIDEO：** 链路入口先聚齐一帧；每一层各自最多 2 帧等待，加 1 帧正在发送。拥塞时丢该层最老的完整等待帧，等待帧 TTL 350 ms。正在发送的帧保留到完成，允许在分片间插入控制/遥测；超过 1500 ms 才放弃剩余片。两层优先级为 `CONTROL > DATA > VIDEO_BASE > VIDEO`，基础层可在分片之间抢占正在发送的高清帧，因此高清帧积压不会拖住基础层。
- **分层视频（默认开启）：** 每次采集编码两层。基础层 160×90 q40（合成画面约 2 KB，15 FPS 约 250 kbps）每帧必发，是保证画面不断的底线。高清层从 7 档阶梯中选择装得进预算的最大一档：640×360 q50/q35/q22、480×270 q30/q18、320×180 q30/q20（合成画面约 22.8 KB 到 3.8 KB，每档约 0.75 倍）；最低档也装不下时暂停高清层。降档立即生效；升档每帧最多一档，并且要用实际编码结果确认只占预算的 80% 以内，避免在两档之间来回跳。
- **高清层预算：** 链路按 `min(标称容量 − 高优先级实测速率, 高清帧实测获得的速率) × 帧间隔 × 0.85` 给出每帧字节预算。这相当于假设是一套自研 MAC（方案中的路线 B），它知道自己的当前速率和各类负载；实测项用来修正标称速率高估的有效吞吐。FIFO 模式不提供预算，高清层固定用最高档，代表拿不到内部信息的黑盒 FIFO 模组。
- **高清层 FEC（默认开启）：** GF(2⁸) 上的系统 Reed-Solomon 纠删码，校验矩阵用 Cauchy 矩阵。k 个数据片照常发送，其后跟 m 个冗余片，**任意 k 片到齐**即可还原整帧；接收端只解缺失的那几片。m 取能让整帧在实测丢包率下以 ≥99% 概率还原的最少包数，上限为 k（合成画面 20 片的高清帧：1% 丢包配 2 片，5% 配 4 片，10% 配 7 片），没测到丢包时 m=0、完全不额外占带宽。测到平均连丢 ≥1.5 个包时，m 还会按「几何分布 95 分位突发在交织后打在同一码字上的片数」再取较大值（5% 丢包、平均连丢 4 时约 6 片，连丢 8 时约 8 片，连丢 16 时约 16 片，上限仍是 100% 开销），并计入高清层字节预算。丢包率由链路按全部业务统计，同时维护 0.5 秒和 2 秒两个窗口、取较大值：丢包开始时半秒内就能跟上，短窗口偶尔运气好也不会立刻撤掉保护。FIFO 模式不给丢包率，也就不加 FEC。基础层不加：它每帧只有 2 片、在 5% 丢包下仍有 90% 能到，而加 1 片冗余就让基础层码率增加一半，抬高了画面不断所需的最低容量。帧级统计也按 FEC 处理：一帧只有在缺的片数超过它的冗余片数、确定无法还原时才记为丢失。
- **突发交织：** 独立丢包（平均连丢 < 1.5）时高清帧仍整帧连续发送，时延与原来相同。测到更长突发后，Fusion 调度器等到凑够交织深度的高清帧再轮流送分片（深度 2 约再等 70 ms，深度 3 约 140 ms；平均连丢 ≥6 时用 3）。一串连续丢失被摊到这几帧上，而不是打穿同一码字。链路空闲插入空白并不能打断按包推进的 Gilbert 突发，所以凑不齐时等到时限就单独发送，不会靠空等拉开同一帧的分片。FIFO 模式不交织。
- **地面选层：** 画面只前进、不回退。基础层重组完成后先等同一次采集的高清帧：高清帧在等待期内到达，就直接显示高清，这个基础层不显示，画面不会在清晰和模糊之间闪烁；等不到（高清帧丢失或来得太晚），就在等待期结束时显示基础层，丢一帧高清只损失清晰度、不损失流畅度。等待时长跟随最近 32 帧“高清比基础层晚到多久”的 P95 加 10 ms，限制在 20～150 ms（实测 1～5 Mbps 下约 49～64 ms，1～5 Mbps 无丢包时没有出现先糊后清的闪烁）。最近 8 帧都没收到高清（高清层暂停或关闭），或高清层普遍晚于 150 ms 时，基础层不等待、立即显示。等待期过后才到的高清帧仍可替换同一次采集的基础层（记为“晚到高清”）。决策逻辑在 `ground_node.LayerSelector`，不依赖 asyncio，可以单独测试。分层是 simulcast 形式：高清层是独立可解码的完整 JPEG，不是叠加在基础层上的残差，代价是基础层码率在高清正常时属于冗余（1.5 Mbps 下约 17%，5 Mbps 下约 5%）。
- **FIFO：** 全业务共用一个按到达顺序发送的队列，不执行新鲜度优化；为了避免无限占内存，队列上限 4 MiB，超过上限丢新到包。
- **带宽：** 双向共用一条虚拟发送时间线：每包从“链路空闲且该包就绪”的时刻开始，占用恰好 `字节数 × 8 / 容量` 的时间，非抢占串行；链路空闲后才选下一个包，所以期间到达的高优先级包仍能抢到下一个时隙。Fusion 视频的就绪时刻是整帧聚齐的时刻。计费包含应用头、分片头和 IPv4/UDP 的 28 字节，不包含真实无线 MAC、编码或重传开销。积压时实际速率等于配置容量（实测 0.5～10 Mbps 均为 99.9%～100%），不会超过。
- **传播：** 每包串行发送完成后，附加 `max(0, delay + uniform(-jitter, jitter))`。传播可以和后续包发送重叠。随机丢包仍消耗带宽，不重传；没有 FEC 保护的 JPEG 任一片丢失就整帧失效。调度主动丢帧与信道随机丢包分别统计。
- **丢包模型：** 两状态（Gilbert）信道，由平均丢包率 `loss` 和平均突发长度 `loss_burst`（连续丢失的包数）两个参数决定：信道处于“坏”状态时丢包，每个包以 `1/loss_burst` 的概率恢复为“好”，以 `loss/(loss_burst·(1−loss))` 的概率变“坏”，长期丢包率恰好是 `loss`，每串连丢平均 `loss_burst` 个包。`loss_burst` 为 1（默认）或不超过 `1/(1−loss)` 时就是独立随机丢包，而且随机数的抽取方式与引入突发之前完全相同，所以默认配置下以前的实验逐包可复现。状态按包推进，与速率无关；改动丢包参数时信道从“好”状态重新开始。网页里是“丢包突发长度”滑块，命令行是 `--burst`，接口是 `/api/link` 的 `loss_burst`（1～50）。
- **重组：** 支持乱序与重复片，最多 32 帧，首片到达后 2 秒未聚齐则清理。已显示更新帧后，不回退显示更老帧；控制也不会因为抖动乱序回退执行旧状态。
- **计时：** 单机统一使用高分辨率单调时钟。Windows 启动时临时请求 1 ms 定时分辨率，结束时恢复；自定义 asyncio loop 同时匹配 `perf_counter` 的时钟与定时器合并精度，防止 Python 3.12 默认 15.6 ms 时钟使传播回调提前触发。另用 Python 高分辨率休眠线程每约 1 ms 唤醒事件循环，避免后台 Windows 计时把每个小控制包的串行发送都拖长到一个系统时钟周期；该线程不操作业务队列，退出时停止。
- **主机计时误差如何处理：** 这台 Windows 主机上 `asyncio.sleep` 每次约多睡 0.5～1 ms。发送循环睡到“虚拟完成时刻”而不是固定时长，醒晚了下一个包仍从虚拟完成时刻接着发，所以误差不会累积成链路空闲。时间线最多落后墙钟 20 ms；主机卡顿超过这个长度时，超出部分记为丢失的空口时间，不事后补发。残留影响只在投递时刻：投递比模型时刻晚 P50 约 0.5 ms、P95 约 1.4 ms，各类业务的时延会因此略微偏大，但不影响速率。两项都进入指标：`link_pacing_efficiency`（未丢失的空口时间占比，正常为 1.0）和 `link_dispatch_late_ms`（投递偏差分布）。

面板延迟和速率使用最近 **5 秒**，计数器使用整个运行期。帧按采集时刻计：任一层被显示即算接收，所有层都未显示才算丢弃；帧丢弃率是 `已丢弃 / (已丢弃 + 已成功接收)`，尚在排队/在途/重组的帧不进入分母。有效 FPS 只计完整重组、JPEG 解码校验成功、按顺序新显示的采集时刻，高清层替换同一时刻的基础层不重复计数；**不是浏览器实际屏幕刷新率**。“高清占比”是新显示画面中高清层的比例；“最长冻结”是窗口内画面两次更新之间的最长间隔，包括窗口结束时仍在持续的冻结。视频延迟截至地面端把它设为当前画面：完整重组，加上分层时基础层等待高清帧的时间（2026-09-11 前只算到重组完成），不包含浏览器渲染；FPS 和最长冻结也按这个时刻统计。“画面年龄”则持续反映当前图像有多旧。

严格优先级只能在控制业务本身还有足够带宽时维持低延迟；极低容量、过大传播时延或严重丢包时仍会退化。基础层 15 FPS 需要约 250 kbps，加上遥控和遥测约需 320 kbps；低于此容量时基础层也会降帧。FEC 的 i.i.d. 冗余量按独立随机丢包计算；长突发改为 2～3 帧交织并略增冗余，而不是把开销加到 70%～195%（那是同一帧内只靠加片才能扛突发 4～16 的数字，见 `VERIFICATION.md` 交织前的基线）。丢包刚开始时的最初几帧还没有冗余、也还没有第二帧可交织，这是任何按实测配置的方案都有的过渡期。关闭 FEC 且有丢包时画面不会停顿，但高清帧大量丢失，画面会频繁在清晰和模糊之间切换（5% 丢包下约 35% 为高清），而且替补显示的基础层要多等一个等待期，视频延迟比有 FEC 时略高。单链路 UDP 仪表盘 MVP 仍是一空一地；多节点能力在 `multinode.py` 调度仿真中验证。SBUS/MAVLink/失控与鉴权为纯软件编解码与状态机（`interfaces.py` / `auth.py`），不接真实飞控或射频。不含 H.264/H.265、Mesh、OFDM/PHY。

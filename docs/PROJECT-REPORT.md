## 1. 项目概述与目标

### 1.1 要解决什么问题

本仓库对应的工程对象是 **Nebula-7 类无人系统“图传 + 数传 + 遥控”一体化无线链路**：一条链路同时承载三类物理性质完全不同的业务。合并方案文档 `图数遥一体化链路_合并版.md`（v1.0，2026-09-10）把官方公开信息整理为：

| 项目 | 官方公开内容（方案【官方】） | 工程解读（方案原文） |
|---|---|---|
| 业务类型 | 同一链路承载视频、状态数据和控制指令 | 不限于单向图传 |
| 网络结构 | 星型，最多 1 个中心节点连接 16 个终端 | 不能据此推定 Mesh、多跳或中心自动接管 |
| 时延 | 两节点网络测试时延 ≤15 ms | 不能直接当作视频端到端时延，也不能外推到 16 节点满载 |
| 距离 | 最远 12 km，限定通视空对地 | 取决于型号、频段、功率、天线与环境 |
| 对外接口 | ETH ×2、UART ×2、SBUS ×1、USB 2.0 | 电平、针脚、方向、速率仍需完整规格书 |

官方品牌为 SINAVE，网站对应主体为广州燎疆科技创新有限公司（见 `方案.txt`、`图数遥一体化链路_合并版.md`）。方案反复强调：**不能仅凭“双天线 / 低时延 / 星型组网”断言该产品使用了 OFDM、MIMO、TDMA、AES-256 或某款芯片。** 第二章讲的是“这类系统可以怎么做”，不是“它就是这么做的”。

三类业务的冲突是设计难点（方案 §2.2）：

| 业务 | 方向 | 带宽量级 | 时延 | 可靠性 | 数据特征 |
|---|---|---|---|---|---|
| 图传 | 机→地为主 | 2–20 Mbps | 100 ms 级可接受 | 允许丢帧 | 突发、大包、速率可变 |
| 数传 | 双向 | 10–500 kbps | 中 | 需重传保证 | 周期小包 + 突发 |
| 遥控 | 地→机 | < 10 kbps | 极低且抖动要小 | 极高，不能丢 | 严格周期（如 SBUS 14 ms） |

建议处理原则：实时控制“过期即丢”、遥测保证最低带宽、视频自适应降码率。复用方式在方案里写为 **TDD 帧结构 + 时隙划分 + QoS 优先级调度**（遥控固定预留，图传占用剩余带宽）。这是同类系统的可行实现路径，**不是已确认的 Nebula-7 内部机制**。

### 1.2 两条技术路线，以及本仓库实际交付了哪一条

`图数遥一体化链路_合并版.md` 把推进拆成两条路线：

- **路线 A（优先）**：成品集成先行验证。目的不是证明宣传指标，而是尽快回答“成品能否满足实际业务、哪些能力必须由外部系统补充”。立项第一道门槛是：**完整规格书 + 双节点测试报告 + 多节点拥塞测试结果**。自研应由明确能力缺口驱动，而不是仅凭“12 km、15 ms、16 节点”三个独立数字启动。
- **路线 B**：自研同类链路（原型建议 SDR：AD9361 + Zynq/ZU+ FPGA）。目标是实现相近业务能力，**不是默认与 Nebula-7 无线互通**。方案明确：在成品尚未验证前直接启动自研，是把最贵的路径放在最前面。物理层 OFDM 仿真按方案 §4.4 / 审查意见 **应等路线 A 结论后再启动**，本仓库正确地没有做。

本仓库当前可运行的软件，属于路线 A 的 **算法与验收骨架**，外加路线 B 在 MAC/调度层可以提前验证的部分，而不是射频、FPGA 或实机固件。

### 1.3 本仓库 MVP 的明确目标与非目标

`README.md` 开篇定义：这是一个 **可运行的单机实验**——JPEG 视频、10 Hz 模拟遥测、50 Hz 遥控状态，通过 **同一个受限双向 UDP 链路** 传输。用 FIFO 与 Fusion 两种调度器对比拥塞下的控制延迟；视频默认分层发送；高清层带 Reed-Solomon FEC；测到长突发时对相邻 2～3 帧高清分片交错发送。

**它验证算法机制，不复现 NEBULA-7 的射频、硬件或实机性能。** 网页页脚同样写明“算法验证 · 单节点 · 共享半双工模型”。界面文案写“单机模拟实验 / 不代表 NEBULA-7 实机性能”。

非目标（`README.md` 末段与方案对照）：

- 不含 H.264/H.265、Mesh、OFDM/PHY。
- 单链路 UDP 仪表盘 MVP 仍是一空一地；多节点能力在 `nebula_mvp/multinode.py` 的 **调度层离散事件仿真** 中验证，不是多进程/多机 UDP 组网。
- `interfaces.py` / `auth.py` 为纯软件编解码与状态机，**不接真实飞控或射频**。
- HTTP 只用于本机画面展示、观测指标、键盘输入和模拟器设置，**不消耗模拟无线带宽**。

### 1.4 应用假设（方案 V0.1 需求基线，不是厂家承诺）

`方案.txt` 与合并版 §3 给出立项讨论用的 V0.1 基线：民用无人机或移动机器人；双向控制、遥测及视频回传；**先验证 1 中心 + 4 终端，再扩展到 1 + 16**。容量核算（每终端视频 4 Mbps、控制与遥测 0.2 Mbps，平均负载控制在已测稳定容量的 70% 以内）：

- 4 个终端：约需 **24 Mbps** 稳定应用有效容量；
- 16 个终端：约需 **96 Mbps** 稳定应用有效容量。

结论写进方案：**16 路高清视频并发不成立**；实际使用必须是全部终端保遥控+遥测，只有被点名的少数终端回传主码流。`docs/multinode-summary.md` 用调度仿真复核了同一结论（见第 6 节）。

## 3. 系统架构与协议链路

### 3.1 三个节点，一个进程，一条共享半双工瓶颈

`README.md` 结构图（实现层面）：

```text
Air Node                                        Ground Node
  OpenCV ─┬→ 160×90 JPEG ─ VIDEO_BASE ─┐   ┌──→ 分层重组(FEC 还原) → 选层 → 解码校验 → 网页视频
          └→ 阶梯选档 JPEG + FEC ─ VIDEO┤   │
             ↑ 高清层预算 / 丢包率      │   │
  模拟飞控 10 Hz ────────── DATA ──────┤   ├──→ 遥测与机载控制值
                                      ▼   │
                              Link Emulator
                           同一个共享发送调度器
                           同一条虚拟发送时间线
                            同一个串行发送资源
                            延迟 / 抖动 / 丢包
                                      ▲   │
  执行模拟控制 ←─────────── CONTROL ───┘   └──── 键盘状态 → 50 Hz
```

实现要点（`app.py`）：

- Air / Ground / Link 是 **一个 Python 进程里的三个独立 asyncio UDP endpoint**，各自绑定 `127.0.0.1` 随机端口，`SO_RCVBUF` 提到 1 MiB。它们确实通过 socket 收发，便于单命令启动和同一时钟计时；**本版没有拆成三个独立进程**。
- 网页默认 `http://127.0.0.1:8765`。HTTP 只服务本机（`Host` 必须是 `127.0.0.1` 或 `localhost`，否则 403）。Ground Node 收到键盘状态后仍必须发出 CONTROL UDP，经链路调度、限速和时延后才到达 Air Node。网页视频只读取 Ground Node 已重组并解码校验的 JPEG。
- 没有打开网页时，Ground Node 仍以 50 Hz 发送中立控制，方便无界面实验。网页以 10 Hz 更新操作状态。

### 3.2 应用层协议

网络字节序，固定头 **18 字节**（`protocol.py`：`HEADER = struct.Struct("!2sBBIQH")`）：

| 字段 | 字节 | 定义 |
|---|---:|---|
| magic | 2 | `N7` |
| version | 1 | **2**（加入 FEC 时分片头变更；版本 1 的包会被拒收） |
| type | 1 | VIDEO=1（全分辨率层），DATA=2，CONTROL=3，VIDEO_BASE=4（基础层） |
| sequence | 4 | 无符号序号 |
| timestamp | 8 | `perf_counter_ns()` 生成时间 |
| payload_length | 2 | 载荷长度 |

约束：

- 每个 UDP 应用数据报最多 **1200** 字节；IPv4/UDP 开销按 **28** 字节计费。
- VIDEO / VIDEO_BASE 载荷前 **12** 字节：`frame_id:uint32, fragment_id:uint16, fragment_count:uint16, frame_bytes:uint32`。因此每片 JPEG 最多 **1170** 字节。
- `fragment_count` **包含 FEC 冗余片**；数据片数由 `frame_bytes` 向上取整除以 1170 算出；编号在数据片之后的是冗余片，长度等于第一个数据片。
- 任何一片都描述了整帧布局，接收端从任意片就能开始组帧。同一次采集的两层共用 `frame_id` 和时间戳。
- DATA / CONTROL 载荷是 JSON。控制四轴：`throttle, yaw, pitch, roll`。
- 时钟不适用于跨电脑直接测单程延迟；将来拆成多台电脑需要时钟同步或往返测量。

重组（`FrameAssembler`）：支持乱序与重复片，最多 **32** 帧，首片到达后 **2 秒**未聚齐则清理。任意 `data_count` 片到齐即可还原（冗余片填缺口）。已显示更新帧后不回退更老帧；控制也不会因为抖动乱序回退执行旧状态。

### 3.3 业务生成与安全边界（MVP 内的玩具模型）

| 业务 | 生成 | 交付 |
|---|---|---|
| 视频 | Air `video_loop`，默认 15 FPS；分层时先发基础层再发高清层，避免高清占住入口 | Ground 重组 → JPEG 解码校验 → `LayerSelector` → `/stream` 或 `/frame.jpg` |
| 遥测 | Air `telemetry_loop`，10 Hz；JSON 含高度、速度、电量、航向、位置、已执行控制、`failsafe` | Ground 只接受更新的生成时间戳 |
| 遥控 | Ground `control_loop`，50 Hz；网页心跳丢失 1 秒则地面输入归中 | Air 只接受更新的生成时间戳；生成时间超过 **500 ms** 的控制不用于运动模型 |

`telemetry.py` 注释与 README 一致：这是模拟模型行为，**不是飞控失效保护实现**。窗口失焦会归中。摄像头图像仅在本机内传输，默认不保存图像文件。界面不依赖 Node、npm、CDN 或外部服务。

### 3.4 链路模型（不是射频）

`link_emulator.py` 把双向流量送进 **同一条虚拟发送时间线**：

- 每包从“链路空闲且该包就绪”的时刻开始，占用恰好 `字节数 × 8 / 容量` 的时间，非抢占串行。
- 计费包含应用头、分片头和 IPv4/UDP 的 28 字节，**不包含真实无线 MAC、编码或重传开销**。
- 积压时实际速率等于配置容量（`VERIFICATION.md` 计时修复后：0.5～10 Mbps 均为 99.9%～100%），不会超过。
- 传播：串行发送完成后附加 `max(0, delay + uniform(-jitter, jitter))`。传播可以和后续包发送重叠。
- 随机丢包仍消耗带宽，不重传。没有 FEC 保护的 JPEG 任一片丢失就整帧失效。调度主动丢帧与信道随机丢包分别统计。
- 丢包模型：两状态 Gilbert 信道，参数为平均丢包率 `loss` 和平均突发长度 `loss_burst`。`loss_burst` 为 1（或不超过 `1/(1−loss)`）时退化为独立随机丢包，且随机数抽取方式与引入突发前完全相同，默认配置下以前的实验逐包可复现。状态按包推进，与速率无关。接口：网页滑块「丢包突发长度」、CLI `--burst`、`/api/link` 的 `loss_burst`（1～50）。
- 容量合法范围 100 kbps–10 Mbps；传播 0–500 ms；抖动 0–200 ms；丢包 0–25%。

主机计时：Windows 上 `asyncio.sleep` 曾每次约多睡 0.5–1 ms。现用虚拟时间线追赶，最多落后墙钟 **20 ms**；更长卡顿记为丢失的空口时间，不事后补发。指标：`link_pacing_efficiency`（未丢失空口时间占比，正常 1.0）和 `link_dispatch_late_ms`（投递偏差；修复后 P50≈0.5 ms、P95≈1.3–1.4 ms）。`--verify` 要求节拍效率 ≥0.98、投递 P95 < 5 ms，否则判定本次无效。

## 4. 调度、FEC 与分层视频设计

### 4.1 FIFO vs Fusion

**FIFO（`mode=naive`）**：全业务共用一个按到达顺序发送的队列，不执行新鲜度优化；队列上限 **4 MiB**，超过则丢新到包。FIFO **不提供**高清层预算、丢包率估计和交织——代表拿不到内部信息的黑盒 FIFO 模组。这对应方案 §4.3 的核心风险：**外部网关的优先级标记不等于无线模块内部一定执行同样的优先级**。MVP 用 FIFO 组把该风险变成可对照的实验。

**Fusion**：链路空闲才问调度器要下一个包，避免低优先级包占住调度器。优先级：

```text
CONTROL > DATA > VIDEO_BASE > VIDEO
```

规则（`README.md` + `scheduler.py` + `config.py`）：

| 队列 | 行为 |
|---|---|
| CONTROL | 一个最新值槽，最高优先级，**100 ms TTL**；新到替换旧值（`control_replaced`） |
| DATA | 最多 **100** 包，超过丢最老；**500 ms TTL** |
| VIDEO / VIDEO_BASE | 链路入口先聚齐一帧（含 FEC 冗余片）；每一层各自最多 **2** 帧等待（交织深度 3 时提高到 3），加正在发送的帧。等待帧 TTL **350 ms**。正在发送的帧保留到完成，允许在分片间插入控制/遥测；超过 **1500 ms** 才放弃剩余片 |
| 基础层抢占 | 基础层可在分片之间抢占正在发送的高清帧，因此高清积压不会拖住基础层 |

### 4.2 分层视频（默认开启）

每次采集编码两层（simulcast，高清层是独立可解码的完整 JPEG，不是残差）：

- **基础层**：160×90 q40，合成画面约 **2 KB**，15 FPS 约 **250 kbps**，每帧必发，是保证画面不断的底线。基础层不加 FEC：每帧只有 2 片，5% 丢包下仍有约 90% 能到；加 1 片冗余会让基础层码率增加一半，抬高“画面不断”所需的最低容量。
- **高清层**：从 7 档阶梯选装得进预算的最大一档（`video.py`）：640×360 q50/q35/q22、480×270 q30/q18、320×180 q30/q20。合成画面约 **22.8 KB 到 3.8 KB**，每档约 0.75 倍。最低档也装不下时暂停高清层。降档立即生效；升档每帧最多一档，且要用实际编码结果确认只占预算的 **80%** 以内，避免两档之间来回跳。

高清层预算（仅 Fusion）：

```text
min(标称容量 − 高优先级实测速率, 高清帧实测获得的速率) × 帧间隔 × 0.85
```

这相当于假设一套自研 MAC（方案路线 B）知道当前速率和各类负载；实测项用来修正标称速率高估的有效吞吐。FIFO 不给预算，高清层固定最高档。

基础层 15 FPS 需要约 250 kbps，加上遥控和遥测约需 **320 kbps**；低于此容量时基础层也会降帧。1.5 Mbps 下基础层码率约占 17%，5 Mbps 下约占 5%（高清正常时这笔是冗余开销）。

### 4.3 地面选层（`ground_node.LayerSelector`）

画面只前进、不回退。规则（2026-09-11 起，见 `VERIFICATION.md`「地面选层改为等待同一帧的高清」）：

1. 基础层重组完成后，先等同一次采集的高清帧。
2. 高清在等待期内到达：直接显示高清，该基础层不显示，避免清晰/模糊闪烁。
3. 等不到：等待期结束时显示基础层——丢一帧高清只损失清晰度、不损失流畅度。
4. 等待时长 = 最近 32 帧「高清比基础层晚到多久」的 P95 + 10 ms，限制在 **20～150 ms**。实测 1～5 Mbps 下约 49～64 ms；1～5 Mbps 无丢包时没有出现先糊后清的闪烁。
5. 最近 8 帧都没收到高清，或高清层普遍晚于 150 ms：基础层不等待、立即显示。
6. 等待期过后才到的高清仍可替换同一次采集的基础层（记为「晚到高清」）。

该对象不依赖 asyncio，可单独单测。修改效果（同一基准，`VERIFICATION.md`）：5% 丢包分层无 FEC 显示帧率从 8.2 FPS 升到 13.4～13.6 FPS；最长冻结从 240 ms 降到 150～199 ms；5 Mbps→500 kbps 骤降后 3 秒内最长冻结从 203 ms 降到 117～119 ms。代价是替补基础层要多等一个等待期。

指标口径：有效 FPS 只计完整重组、JPEG 解码校验成功、按顺序新显示的采集时刻；高清替换同一时刻的基础层不重复计数；**不是浏览器实际屏幕刷新率**。视频延迟截至地面端把它设为当前画面（含等待），不包含浏览器渲染。「画面年龄」持续反映当前图像有多旧。「最长冻结」含窗口结束时仍在持续的冻结。

### 4.4 高清层 FEC

`fec.py`：GF(2⁸) 系统 Reed-Solomon，校验矩阵用 Cauchy 矩阵（`1/(x_j+y_i)`，本原多项式 `x^8+x^4+x^3+x^2+1`）。k 个数据片照常发送，其后跟 m 个冗余片，**任意 k 片到齐即可还原**；接收端只解缺失的数据片。块数上限 255。生存目标 `SURVIVAL_TARGET = 0.99`。

m 的选取：

- 独立丢包：取能让整帧在实测丢包率下以 ≥99% 概率还原的最少包数，上限为 k。合成画面约 20 片的高清帧：1% 丢包配 2 片，5% 配 4 片，10% 配 7 片。没测到丢包时 m=0，完全不额外占带宽。
- 测到平均连丢 ≥1.5 个包时，m 再按「几何分布 95 分位突发在交织后打在同一码字上的片数」取较大值（README：5% 丢包、平均连丢 4 时约 6 片，连丢 8 时约 8 片，连丢 16 时约 16 片，上限仍是 100% 开销），并计入高清层字节预算。

丢包率由链路按 **全部业务** 统计，同时维护 **0.5 秒和 2 秒** 两个窗口、取较大值：丢包开始时半秒内就能跟上，短窗口偶尔运气好也不会立刻撤掉保护。FIFO 不给丢包率，也就不加 FEC。

帧级统计：一帧只有在缺的片数超过冗余片数、确定无法还原时才记为丢失。`VERIFICATION.md` 另用 300 组随机丢片组合（1～23400 字节、1～8 片冗余）验证编解码，全部还原。

### 4.5 突发交织

独立丢包（平均连丢 < 1.5）时高清帧仍整帧连续发送，时延与原来相同。测到更长突发后，Fusion 等到凑够交织深度的高清帧再轮流送分片：

- 深度由 `fec.interleave_depth`：`<1.5` → 1；`<6` → 2；否则 3。
- 深度 2 约再等 **70 ms**，深度 3 约 **140 ms**（`INTERLEAVE_HOLD_NS = 70_000_000`，约一个 15 FPS 采集间隔）。
- 一串连续丢失被摊到这几帧上，而不是打穿同一码字。
- 链路空闲插入空白并不能打断按包推进的 Gilbert 突发，所以凑不齐时等到时限就单独发送，不会靠空等拉开同一帧的分片。
- FIFO 不交织。深度超过 3 会把等待推过约 250 ms 的视频预算，因此硬封顶为 3。

交织前的解析基线（`VERIFICATION.md`，一帧 20 数据片、平均丢包 5%、包在信道上连续排列）：保 99% 还原所需冗余在突发 4/8/16 时分别为 14/23/39 片，开销 70%/115%/195%。结论：同一帧内的纠删码只对长度不超过约 1～2 个包的丢失有效；更长突发单靠加冗余开销太大。交织后的验收上限见第 5 节。

丢包刚开始时的最初几帧还没有冗余、也还没有第二帧可交织——任何按实测配置的方案都有这段过渡期。关闭 FEC 且有丢包时画面不会停顿，但高清帧大量丢失，画面会频繁在清晰和模糊之间切换（5% 丢包下约 35% 为高清），替补基础层还要多等一个等待期。

### 5.2 网页对照实验（README 操作步骤）

1. 选 FIFO，容量 5 Mbps，等指标稳定。
2. 降到 500 kbps，保持 10 秒以上，观察 FIFO 队列和遥控 P99。
3. 切 Fusion，保持相同容量，等 5 秒滚动窗口更新。

6. 切回分层，容量逐级调到 1.5、5 Mbps，观察高清档位。
7. 保持 5 Mbps，随机丢包 5%：FEC 开启时画面几乎全是高清；关闭后高清占比降到约三分之一，但画面仍流畅。

### 6.2 多节点仿真结论（决策用，模型假设）

命令：`.venv/bin/python -m nebula_mvp.multinode --n 16 --mbps 40`。`docs/multinode-summary.md`：

1. **16 节点能跑几路主视频？** 40 Mbps + `fusion_fair`、全部终端保控制+遥测时，调度器最多给 **10** 路并发约 4 Mbps 主视频每路 ≥3.5 Mbps；k≥11 时公平均分后每路约 2 Mbps，可用列变为 0。§2.6 70% 余量算法约 **6** 路。16 路 HD 不成立（需约 96 Mbps 稳定容量）。
2. **弱链路会不会拖垮别人？** 共享 12 Mbps、弱节点效率 0.25 开主视频：FIFO 旁观控制 P99 **904.4 ms** vs `fusion_fair` **18.5 ms**（约 49 倍）。
3. **切主源时他人遥控是否中断？** 节点 0→1 于 t=2.0 s，旁观节点控制 P99 切换前后均为 **6.9 ms**。

业务含义（文档原文）：全部终端保遥控+遥测；主码流按需点名；调度需节点间公平/隔离，否则弱链路或 FIFO 会拖垮全网控制。

## 7. 已知限制与风险

### 7.1 MVP 自己写明的模型边界

来自 `README.md` 末段与实现注释，必须原样理解：

- **严格优先级只能在控制业务本身还有足够带宽时维持低延迟**；极低容量、过大传播时延或严重丢包时仍会退化。
- 计费不含真实无线 MAC、编码、重传；半双工共享时间线也不是 TDD 时隙表。
- FEC 的 i.i.d. 冗余按独立随机丢包计算；长突发靠 2～3 帧交织并略增冗余，而不是把开销加到 70%～195%。
- 丢包开始后的过渡期无法避免（第一帧发出时还没观测到丢包）。
- 关闭 FEC 时分层能保流畅，但不能保高清占比。
- 单机统一单调时钟；不能把本机 `perf_counter` 时延当成跨机单向时延。
- `SimulatedFlight` / 500 ms 过期不执行 / 网页 1 秒归中，都是玩具模型，不是 PX4 式失联保护。
- 主机过忙时空口时间丢失；`--verify` 会直接判无效（`VERIFICATION.md` 曾有一次 Fusion 占用仅 46%、0.4 FPS 的异常运行，已不计入结论）。

### 7.2 方案风险清单（合并版 §7）与本仓库的对应关系

| 方案风险 | 影响 | 本仓库已做 / 未做 |
|---|---|---|
| **外部 QoS ≠ 模块内部 QoS** | 网关标了优先级但模块仍 FIFO | MVP 用 FIFO vs Fusion 对照把该坑变成可演示实验；**真模组内部是否有 QoS 仍【待核实】** |
| 12 km 与高吞吐不可兼得 | 需求冲突、对外承诺失实 | 链路预算说明余量只对应窄带低阶工作点；方案要求距离与吞吐分档 |
| 16 节点带宽不足 | 体感与宣传不符 | 仿真：40 Mbps 下约 10 路原始填满 / 6 路 70% 余量；16 路 HD 不成立 |
| **频段合规（1.4 GHz）** | 无法合法使用或只能单向 | 计算器标注 “physics only; CN compliance separate”；未做法规结论 |
| 中心节点单点故障 | 全网瘫痪 | 【待核实】厂商是否有接管；MVP 未建模 |

| 远距离保护间隔不足 | 多节点时隙碰撞 | 方案示例 GP 0.2 ms，12 km 传播约 40 μs；MVP 无时隙表 |
| 数值被误当作规格 | 对外失实 | 合并版 §0 标注纪律；本报告沿用 |

### 7.3 审查留下的认知风险（即使代码已修）

- `docs/REVIEW-a9cb9d8.md`：**48 项现有测试通过不能替代边界验收。** 公平调度复核只证明该过载场景不再饿死节点，不等于已验证不同包长、不同链路效率下的带宽或空口时间公平性。

相对方案功能需求 F-01～F-11 与性能表：自动入网、二层网桥、UART 透传、真实 SBUS 周期输出、选频抗干扰、管理 API（RSSI/SNR/MCS）、断链重连 <3 s、空口加密、OTA、外场距离、示波器空口时延、H.265 视频端到端、16 台真终端并发——**均未在本仓库实现或实测**。当前软件证明的是：在共享半双工 UDP 模型里，新鲜度优先调度 + 分层 + 按实测配置的纠删码 + 有限交织，可以使遥控 P99 在拥塞和 5% 丢包下保持约 **27–45 ms**，同时用基础层保住画面不断。
